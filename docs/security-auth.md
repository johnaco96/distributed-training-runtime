# Security Authentication & Authorization

## Current auth status

- Coordinator supports optional metadata-based authn/authz via `--auth-mode metadata`.
- mTLS is implemented via `--tls-cert`/`--tls-key`/`--tls-client-ca` coordinator flags.
- Structured audit logging captures auth accept/reject decisions.
- Local/dev flows prioritize reproducibility and functional runtime semantics.

## Why a static token alone is insufficient

Static shared tokens are not a strong long-term model because they:
- Lack strong workload identity binding.
- Increase blast radius when leaked.
- Are hard to rotate safely at scale.
- Do not provide robust mutual peer authentication by themselves.

## Target model

- mTLS for transport security and mutual service identity proof.
- Workload identity for machine actors (SPIFFE/SPIRE-compatible direction where practical).
- Short-lived credentials instead of long-lived static credentials where possible.
- OIDC-backed human/admin authentication for future dashboard/admin surfaces.
- Explicit authorization policy for coordinator RPCs.

## Local/dev token fallback stance

A local/dev token mechanism may be used as a temporary fallback for experiments, but it is not the target production security state.

## Implemented auth capabilities

- Optional TLS/mTLS foundation for coordinator gRPC and Python client.
- Plaintext remains the default local/dev behavior when TLS options are omitted.
- Coordinator TLS options: `--tls-cert`, `--tls-key`, `--tls-client-ca` (enables mTLS when set).
- Python RuntimeClient supports TLS via `tls_ca_cert`, `tls_client_cert`, `tls_client_key` args and corresponding `DTRUNTIME_TLS_*` env vars.
- Authorization mode enabled with `--auth-mode metadata` or `DTRUNTIME_AUTH_MODE=metadata`.
- Python client attaches `x-dtruntime-subject`, `x-dtruntime-role`, and `x-dtruntime-worker-id` via constructor args or env (`DTRUNTIME_AUTH_SUBJECT`, `DTRUNTIME_AUTH_ROLE`, `DTRUNTIME_AUTH_WORKER_ID`).
- Authorization tests cover coordinator RPC groups across admin-only and worker-scoped endpoints including worker self-mismatch denial and missing/invalid identity rejection.

## Secure local Kubernetes path

`k8s/local-secure/` validates TLS/mTLS with real Kubernetes Secrets (`dtruntime-tls`, `dtruntime-client-ca`, `dtruntime-client-tls`) created from generated local certs in `.dtruntime-certs/`. The coordinator consumes `--tls-cert`, `--tls-key`, and `--tls-client-ca` from mounted secret files, and the PyTorch job uses `DTRUNTIME_TLS_CA_CERT`, `DTRUNTIME_TLS_CLIENT_CERT`, and `DTRUNTIME_TLS_CLIENT_KEY`.

TLS hostname verification is kept enabled end-to-end. Development server certificates generated by `scripts/generate_dev_certs.ps1` include SAN coverage for `runtime-coordinator.dtruntime.svc.cluster.local` and related Kubernetes service DNS names. Do not commit generated `.dtruntime-certs/` material.

## Security hygiene reminder

Never commit real tokens, secrets, private keys, kubeconfigs, or cloud credentials.
