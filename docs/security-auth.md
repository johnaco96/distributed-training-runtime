# Security Authentication & Authorization Plan (Phase 20F-1)

## Current auth status

- Coordinator currently does not enforce a production-grade authn/authz model.
- Local/dev flows prioritize reproducibility and functional runtime semantics.

## Why a static token alone is insufficient

Static shared tokens are not a strong long-term model because they:
- Lack strong workload identity binding.
- Increase blast radius when leaked.
- Are hard to rotate safely at scale.
- Do not provide robust mutual peer authentication by themselves.

## Target model

- mTLS for transport security and mutual service identity proof.
- Workload identity for machine actors (SPIFFE/SPIRE-compatible direction where practical).
- Short-lived credentials instead of long-lived static credentials where possible.
- OIDC-backed human/admin authentication for future dashboard/admin surfaces.
- Explicit authorization policy for coordinator RPCs.

## Local/dev token fallback stance

A local/dev token mechanism may be used as a temporary fallback for experiments, but it is not the target production security state.

## Planned 20F-2 scope

- Add optional TLS/mTLS foundation for coordinator gRPC and Python client.
- Preserve clear local/dev compatibility modes while labeling non-production behavior.

## Planned 20F-3 scope

- Add workload identity mapping.
- Add explicit authorization checks for coordinator RPC surfaces.

## Security hygiene reminder

Never commit real tokens, secrets, private keys, kubeconfigs, or cloud credentials.

## Phase 20F-3 authorization scaffolding
Phase 20F-3 adds an internal authorization model with optional metadata-based caller identity for local/dev testing. Default mode remains disabled for compatibility. Enable with `runtime-coordinator --addr 0.0.0.0:50051 --auth-mode metadata` or `DTRUNTIME_AUTH_MODE=metadata`. Python client can attach `x-dtruntime-subject`, `x-dtruntime-role`, and optional `x-dtruntime-worker-id` via constructor args or env (`DTRUNTIME_AUTH_SUBJECT`, `DTRUNTIME_AUTH_ROLE`, `DTRUNTIME_AUTH_WORKER_ID`). This is policy scaffolding only (not full SPIFFE/SPIRE or production RBAC). Audit/security events remain planned for Phase 20F-4; dashboard/HA/production S3 hardening remain Phase 20F-5.
Coordinator-driven examples should call RuntimeClient helper methods (for example `register_run`, `register_worker`, `request_shard`, `heartbeat`, and checkpoint helpers) so configured auth metadata is attached consistently.


Phase 20F-4 adds structured audit/security events; dashboard/SIEM/durable audit storage remain future work (20F-5+). Audit logs may include logical identity and run/checkpoint identifiers and should be protected.


## Phase 20F-3 authorization matrix coverage update
Service-level metadata authorization tests now cover coordinator RPC groups across admin-only and worker-scoped endpoints (including worker self-mismatch denial and missing/invalid identity rejection). This remains local/dev metadata identity scaffolding and is not production identity assurance. Production mTLS/SPIFFE identity extraction and policy integration remain future work.

## Step 3 secure local Kubernetes path
`k8s/local-secure/` now validates TLS/mTLS with real Kubernetes Secrets (`dtruntime-tls`, `dtruntime-client-ca`, `dtruntime-client-tls`) created from generated local certs in `.dtruntime-certs/`. The coordinator consumes `--tls-cert`, `--tls-key`, and `--tls-client-ca` from mounted secret files, and the PyTorch job uses `DTRUNTIME_TLS_CA_CERT`, `DTRUNTIME_TLS_CLIENT_CERT`, and `DTRUNTIME_TLS_CLIENT_KEY`.


Step 3 local secure validation keeps TLS hostname verification enabled end-to-end. Development server certificates generated by `scripts/generate_dev_certs.ps1` include SAN coverage for `runtime-coordinator.dtruntime.svc.cluster.local` and related Kubernetes service DNS names, so clients can securely connect without name overrides. Do not commit generated `.dtruntime-certs/` material.


Step 3 secure Kubernetes validation now enforces identity separation in the Python coordinator-driven example: admin metadata is used for control-plane RPCs (for example RegisterRun/RegisterDataset/CommitCheckpoint), while worker-scoped RPCs use per-worker metadata with matching `x-dtruntime-worker-id`. This preserves coordinator authorization boundaries and prevents admin impersonation of workers.
